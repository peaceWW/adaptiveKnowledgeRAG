


# 企业级 Adaptive Knowledge RAG 完整设计方案

我建议把这个系统定义为：

> **Adaptive Knowledge RAG（自适应知识检索增强系统）**
>
> 它不是简单的“文档 → Chunk → Vector DB → LLM”，而是一个能够根据**知识类型、知识结构、用户问题类型和风险等级**，动态选择不同知识处理与检索策略的企业知识平台。

对于你前面提到的专业芯片设计知识，这套方案尤其适合。

当前主流检索系统已经普遍支持混合检索、向量检索、过滤和重排序，但这些能力只是底层基础设施；真正决定企业专业知识库效果的，是上层如何做知识分类、知识建模和 Retrieval Planning。([Elastic][1])

# 1. 整体设计目标

系统需要解决五个核心问题。

## 1.1 不同知识采用不同理解方式

例如：

| 知识类型   | 核心知识结构             |
| ------ | ------------------ |
| 芯片/科技  | 定义、原理、参数、公式、约束、例外  |
| 历史     | 时间、事件、人物、地点、背景、因果  |
| 法律     | 主体、条件、行为、法条、例外、责任  |
| 故障案例   | 环境、现象、原因、解决方案、预防   |
| API 文档 | 接口、参数、返回值、版本、异常、示例 |
| 企业制度   | 角色、条件、流程、权限、审批     |
| 数学     | 定义、公式、定理、证明、推导、应用  |

因此：

```text
知识类型
    ↓
决定
    ↓
知识模型
    ↓
决定
    ↓
切分策略
+
Metadata
+
关系模型
+
索引策略
+
召回策略
+
完整性规则
```

# 3. 最核心组件：Knowledge Strategy Engine

这是整个系统的“大脑”。

它负责回答两个问题。

---

## 问题一：这个文档是什么知识？

例如：

```text
芯片设计规范
```

识别：

```json
{
  "knowledge_domain": "semiconductor",
  "knowledge_type": "technical_specification",
  "strategy": "TECHNICAL_SPEC_V1"
}
```

而历史文档：

```json
{
  "knowledge_domain": "history",
  "knowledge_type": "historical_event",
  "strategy": "HISTORY_EVENT_V1"
}
```

故障案例：

```json
{
  "knowledge_domain": "engineering",
  "knowledge_type": "incident_case",
  "strategy": "INCIDENT_CASE_V1"
}
```

---

## 问题二：用户到底在问什么？

例如：

> 为什么 CDC 会出现亚稳态？

解析：

```json
{
  "knowledge_domain": "semiconductor",
  "topic": "CDC",
  "intent": "principle_explanation",
  "target_concepts": [
    "CDC",
    "Metastability"
  ],
  "required_knowledge": [
    "definition",
    "root_cause",
    "mechanism",
    "solution"
  ]
}
```

然后系统决定：

```text
不能直接 TopK
```

而是：

```text
CDC
 ↓
Metastability
 ↓
Definition
 ↓
Root Cause
 ↓
Mechanism
 ↓
Synchronizer
 ↓
Design Constraint
```

# 4. Knowledge Strategy 抽象模型

```text

│
├── Classification Rule
│
├── Knowledge Ontology

│
├── Relation Schema
│
├── Index Strategy
│
├── Retrieval Strategy
│
├── Completeness Rule
│
└── Answer Policy
```

Java 可以抽象成：

```java
public interface KnowledgeStrategy {

    KnowledgeType type();

    KnowledgeOntology ontology();

    List<KnowledgeUnit> buildKnowledgeUnits(
            DocumentContext context
    );

    MetadataSchema metadataSchema();

    List<KnowledgeRelation> extractRelations(
            List<KnowledgeUnit> units
    );

    RetrievalPlan buildRetrievalPlan(
            QueryContext query
    );

    CompletenessResult checkCompleteness(
            RetrievalContext context
    );

}
```

然后：

```text
KnowledgeStrategy
│
├── TechnicalKnowledgeStrategy
│
├── TechnicalSpecificationStrategy
│
├── HistoricalKnowledgeStrategy
│
├── LegalKnowledgeStrategy
│
├── IncidentCaseStrategy
│
├── ApiDocumentStrategy
│
└── EnterpriseProcessStrategy
```

注意：

> 不建议一开始做几十种 Strategy。

第一阶段只需要做 5～8 个。

# 6. 不要再使用传统 Chunk，而是 Knowledge Unit

建议定义统一的 Knowledge Unit。

```json
{
  "knowledge_id": "KU-001",

  "knowledge_type": "technical_concept",

  "title": "Setup Time",

  "content": "核心知识内容",

  "semantic_role": "definition",

  "importance": "core",

  "domain": "digital_design",

  "sub_domain": "timing_analysis",

  "concepts": [
    "setup_time",
    "clock",
    "data_path"
  ],

  "dependencies": [],

  "relations": [],

  "parent_id": "SECTION-3.2",

  "source_document_id": "DOC-001",

  "source_position": {
    "chapter": "3",
    "section": "3.2",
    "page": 21
  },

  "version": "v1.0",

  "confidence": 0.96
}
```

核心区别：

```text
传统：

Chunk = 一段文字


Adaptive Knowledge RAG：

Knowledge Unit = 有明确知识语义的知识对象
```

# 10. 分层索引

这里建议建立 4 层索引。

```text
L0 Knowledge Catalog
        ↓
L1 Domain Index
        ↓
L2 Topic / Concept Index
        ↓
L3 Knowledge Unit Index
```

例如：

```text
Semiconductor
│
├── Digital Design
│   │
│   ├── RTL
│   │   ├── FSM
│   │   └── CDC
│   │
│   └── Timing
│       ├── Setup Time
│       └── Hold Time
│
└── Physical Design
```

用户查询：

> 如何解决异步 FIFO 的跨时钟域问题？

系统先：

```text
L0
Semiconductor

↓

L1
Digital Design

↓

L2
CDC / Asynchronous FIFO

↓

L3
Knowledge Unit
```

这样不会在：

```text
1000 万知识块
```

里直接检索。

而是在：

```text
特定 Topic 范围
```

内检索。

向量数据库和搜索引擎本身已经支持过滤与混合检索，例如 Qdrant 的 payload filter 与多阶段 Query API、Milvus 的 metadata filtered search，以及 Elasticsearch/OpenSearch 的 lexical + semantic hybrid search。([Qdrant][2])

# 11. Retrieval Planner

这是查询阶段最重要的组件。

不要：

```text
User Query
   ↓
Embedding
   ↓
Vector TopK
```

而应该：

```text
User Query
      │
      ▼
Query Understanding
      │
      ├── Domain
      ├── Topic
      ├── Intent
      ├── Entity
      ├── Time
      └── Risk
      │
      ▼
Retrieval Planner
      │
      ▼
Retrieval Plan
```

例如：

```json
{
  "domain": "semiconductor",

  "topic": "CDC",

  "intent": "solution_design",

  "retrieval_steps": [
    {
      "type": "catalog_filter",
      "domain": "digital_design"
    },
    {
      "type": "concept_search",
      "concept": "CDC"
    },
    {
      "type": "relation_expand",
      "relations": [
        "cause",
        "solution",
        "constraint"
      ]
    },
    {
      "type": "hybrid_search"
    }
  ]
}
```

# 12. Query Intent 决定召回方式

这是 Adaptive 的关键。

同一个主题，不同问题应该采用不同检索。

例如：

> 什么是 CDC？

```text
Intent:

Definition
```

召回：

```text
Definition
+
Basic Explanation
```

---

> 为什么 CDC 会出现亚稳态？

```text
Intent:

Cause Analysis
```

召回：

```text
Definition
+
Cause
+
Mechanism
```

---

> 如何解决 CDC？

```text
Intent:

Solution
```

召回：

```text
Classification
+
Solution
+
Constraint
+
Example
```

---

> CDC 设计有哪些风险？

```text
Intent:

Risk Analysis
```

召回：

```text
Risk
+
Failure Case
+
Constraint
+
Best Practice
```

因此：

```text
Topic 相同
≠
Retrieval Plan 相同
```

# 13. Hybrid Retrieval

推荐：

```text
                 Query
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
     Keyword     Vector     Graph
        │          │          │
        └──────────┼──────────┘
                   ▼
                Fusion
                   │
                   ▼
                Rerank
```

具体：

## Keyword

负责：

```text
CDC
MTBF
tSU
tH
PCIe Gen5
```

这种精确术语。

---

## Vector

负责：

```text
用户自然语言
```

例如：

> 数据跨时钟域怎么避免不稳定？

找到：

```text
CDC
Metastability
Synchronizer
```

---

## Graph

负责：

```text
关系扩展
```

例如：

```text
CDC
 │
 ├── causes
 │     └── Metastability
 │
 ├── solution
 │     ├── Synchronizer
 │     └── Async FIFO
 │
 └── constraint
       └── MTBF
```

---

## Fusion

可以使用：

```text
RRF
Weighted Score
Dynamic Weight
```

Elastic、OpenSearch、Qdrant 和 Milvus 都提供了不同形式的混合检索或结果融合能力；工程上不建议把某个数据库内置融合算法当成唯一标准，而应允许 Retrieval Planner 根据知识类型和查询意图调整候选集合与权重。([Elastic][1])

# 14. Rerank

建议采用两阶段。

```text
First Stage Retrieval

Keyword Top 50
Vector Top 50
Graph Top 30

↓

Fusion

↓

Top 50

↓

Reranker

↓

Top 10~20
```

不要：

```text
全库 Rerank
```

Rerank 的职责是：

> 高成本模型负责精排，小成本检索负责扩大候选集。

这也是当前混合检索系统的常见工程模式。([Qdrant][3])

# 15. 最重要的部分：Completeness Checker

你的场景不能只检查：

> 找到的内容是否相关。

还必须检查：

> 回答是否覆盖完整。

例如：

> 如何设计异步 FIFO？

先生成 Knowledge Requirement。

```json
{
  "required_topics": [
    "usage_scenario",
    "architecture",
    "gray_code",
    "write_pointer",
    "read_pointer",
    "pointer_sync",
    "full_detection",
    "empty_detection",
    "reset",
    "timing_constraint"
  ]
}
```

然后：

```text
Retrieval Result

✓ Architecture
✓ Gray Code
✓ Pointer Sync
✗ Reset
✗ Timing Constraint
```

发现缺失。

触发：

```text
Secondary Retrieval
```

```text
Missing:
Reset
Timing Constraint

↓

Targeted Search

↓

Merge
```

最终：

```text
Completeness Score = 0.91
```

例如：

```text
> 0.9
允许回答

0.7 ~ 0.9
提示部分知识缺失

< 0.7
继续检索 / 拒绝生成
```

# 16. 高风险知识不能只看 AI Score

对于芯片、法律、医疗、金融等高风险领域，我建议：

```text
Final Confidence
=
Source Authority
+
Retrieval Relevance
+
Knowledge Completeness
+
Cross Source Consistency
+
AI Confidence
```

其中：

```text
AI Confidence
```

权重不能太高。

推荐：

```text
Source Authority      30%
Retrieval Relevance   25%
Completeness          20%
Consistency           15%
AI Confidence         10%
```

实际权重需要根据企业测试集校准。

# 17. Knowledge Graph 的定位

不要犯一个常见错误：

> 把所有文档都塞进 Neo4j。

Neo4j 应该存：

```text
Concept
Event
Rule
Component
Parameter
Knowledge Unit
```

以及关系：

```text
DEPENDS_ON
CAUSES
SOLVES
CONSTRAINS
RELATED_TO
REFERENCES
SUPERSEDES
CONFLICTS_WITH
```

例如：

```text
Setup Time
     │
     ├── RELATED_TO → Hold Time
     │
     ├── AFFECTS → Clock Frequency
     │
     └── DEPENDS_ON → Data Path Delay
```

原文仍然放：

```text
Object Storage
+
Search Engine
+
Vector DB
```

Neo4j 只负责：

> 知识关系导航。

# 19. 技术选型建议

## 方案 A：推荐企业自建版

适合你这种：

> 技术知识复杂、知识量大、准确度要求高。

| 层                   | 推荐                                   |
| ------------------- | ------------------------------------ |
| Backend             | Spring Boot                          |
| Agent Orchestration | LangGraph / 自研 Workflow              |
| Metadata            | PostgreSQL / MySQL                   |
| Keyword Search      | Elasticsearch                        |
| Vector              | Qdrant                               |
| Graph               | Neo4j                                |
| Cache               | Redis                                |
| Object Storage      | MinIO                                |
| MQ                  | Kafka                                |
| OCR                 | PaddleOCR                            |
| Document Parser     | Apache Tika + 专用 Parser              |
| LLM                 | 企业模型网关                               |
| Embedding           | 可替换模型服务                              |
| Reranker            | 独立模型服务                               |
| Observability       | Prometheus + Grafana + OpenTelemetry |

Qdrant 当前支持 dense/sparse/named vectors、payload filtering 和多阶段混合查询；Elasticsearch 则可以把全文、过滤和向量检索组合在一个引擎中。因此企业落地时可以选择“ES + 专用 Vector DB”的双引擎模式，也可以根据团队复杂度选择单一 Elasticsearch/OpenSearch 模式。([Qdrant][4])

    private final Map<KnowledgeType, KnowledgeStrategy> strategies;

    public KnowledgeStrategyRegistry(
            List<KnowledgeStrategy> strategyList

# 最终核心思想

整个 Adaptive Knowledge RAG 可以总结为：

```text
                  ┌──────────────┐
                  │ 原始知识      │
                  └──────┬───────┘
                         ▼
                ┌─────────────────┐
                │ 知识类型识别     │
                └────────┬────────┘
                         ▼
                ┌─────────────────┐
                │ Strategy Engine │
                └────────┬────────┘
                         ▼
        ┌────────────────────────────────┐
        │ 不同知识 → 不同知识处理策略     │
        └────────────────┬───────────────┘
                         ▼
              Knowledge Unit + Metadata
                         ▼
             ┌───────────┼───────────┐
             ▼           ▼           ▼
          Keyword      Vector       Graph
             │           │           │
             └───────────┼───────────┘
                         ▼
                    User Query
                         ▼
                 Query Understanding
                         ▼
                  Retrieval Planner
                         ▼
                 Adaptive Retrieval
                         ▼
                    Rerank
                         ▼
                Completeness Check
                         ▼
                   Verified Answer
```

我认为这套系统最关键的不是 Qdrant、Neo4j 或 Elasticsearch 选哪个，而是建立这三个真正的核心资产：

1. **Knowledge Ontology**：企业如何定义自己的知识。
2. **Knowledge Strategy Engine**：不同知识如何被理解、拆分和存储。
3. **Retrieval Planner + Completeness Checker**：不同问题应该如何寻找知识，以及如何判断“是否找全”。

其中第一版如果是针对你提到的**芯片专业知识库**，我建议不要继续泛化，而是直接先设计一套具体的：

> **Semiconductor Knowledge Ontology + TechnicalKnowledgeStrategy V1**

包括一级到五级知识目录、Definition/Rule/Constraint/Formula/Exception 的数据模型、Knowledge Unit 表结构、Neo4j 节点和关系设计，以及完整的入库和查询时序流程。

这样先把一个高难度专业领域跑通，再抽象成通用的 Adaptive Knowledge RAG 平台，会比一开始就做“万能知识库”更容易真正落地。
