## 图片不能只做 OCR

这是专业论文 RAG 特别容易做错的一点。

比如你上传论文第 7 页 Fig.10/11 是 ADC 架构图和 unit SAR ADC 电路结构。正文明确说明 Fig.10 是完整的 **10 GS/s、6-bit、32-way time-interleaved ADC**，其中 8 个 parallel sub-ADC 工作在 1.25 GS/s，每个又由 4 个 312.5 MS/s asynchronous SAR ADC 构成。

OCR 最多可能得到：

```text
32-way time-interleaved ADC
SAR logic
T/H
DSP
...
```

但真正应该存的是：

```text
Figure Type:
    Architecture Diagram

Components:
    Clock generation
        ↓
    8 × Track-and-Hold
        ↓
    32 × Unit SAR ADC
        ↓
    Digital interface
        ↓
    DSP

Parameters:
    Sampling rate = 10 GS/s
    Resolution = 6 bit
    Unit ADC rate = 312.5 MS/s

Relations:
    Fig.10 → explained_by → Section III.B
    Fig.10 → contains → SAR ADC
    Fig.10 → related_to → Fig.11
```

也就是说：

**OCR负责“看到了什么文字”，Vision LLM负责“这张图表达了什么知识”。**

这两个不要混为一谈。

## 公式同样不能简单转成文本

比如：

```text

```

应该至少保存四份信息：

```text

+

+

```

例如：

```json
{
  "type": "equation",

  "latex":
  "\\alpha_{-1}=\\frac{(... )_2}{32}",

  "meaning":
  "FFE precursor tap coefficient",

  "variables": {
      "alpha_-1": "precursor coefficient",
      "A": "5-bit control word"
  },

  "context":
  "Used by the embedded 3-tap FFE inside SAR ADC",

  "related_figure":

```

这样以后用户问：

> α−1 是怎么算的？

RAG 不只是返回公式，还可以把**公式 + Fig.9 + 原文解释 + Page 6 / Eq.(1)** 一起交给模型。

# 引用体系反而是整个方案最重要的部分

你希望最终回答：

> 为什么这种 ADC 可以降低数字均衡器功耗？

而是类似：

> 该架构首先使用 ADC 内嵌的 3-tap analog FFE 进行部分均衡，再由 digital threshold detector 判断当前 symbol 是否处于可靠区间。如果 symbol 可靠，则 bypass digital equalizer；只有落入 ambiguous region 时才启用 digital equalization。论文报告，在高损耗 channel 下这种方法仍可显著降低数字均衡器的工作比例。

论文自己的身份信息和 DOI 位于首页。

# 我会建议你的存储层拆成 4 类

结合你之前考虑的 Java / Python 企业知识库架构，我会采用：

| 数据                                                            | 存储                     |
| ------------------------------------------------------------- | ---------------------- |
| Document / Section / Page / Figure / Equation / Reference 元数据 | PostgreSQL / MySQL     |

Vector DB 解决：

```text
“和我的问题语义相关的知识是什么？”
```

关系数据库 / Graph 解决：

```text

```

对象存储解决：

```text
“把 Fig.9 原图给我。”
```

这三个职责完全不同。

不要：

```text

 ├ chunk2

 └ chunk4
```

而应该：

```text
Document
│
├── Section II
│    │
│    ├── Concept: Reliable Symbol Detection
│    │      ├── Paragraph
│    │      ├── Fig.2
│    │      └── Fig.3
│    │
│    └── Concept: Hybrid ADC Receiver
│           ├── Paragraph
│           ├── Fig.4
│           └── Fig.5
│
├── Section III
│    │
│    └── Concept: SAR ADC + Embedded FFE
│           ├── Paragraph
│           ├── Fig.9
│           ├── Eq.(1)
│           └── Fig.10
│
└── References
     ├── Ref 1
     ├── Ref 2
     ├── ...
     └── Ref 21
```

**检索最小知识 Node，回答时回溯 Parent Context，同时把关联 Figure / Equation / Citation 一起取出来。**

这正好解决你最开始提出的要求：

> **回答不仅要“知道答案”，还要知道答案来自哪段文字、哪张图、哪个公式、哪一页，以及引用了哪篇论文。**

而你上传的这篇论文非常适合作为这个系统的第一份 benchmark PDF：它同时具备双栏 IEEE Layout、复杂电路图、曲线图、公式、表格、Figure Caption、Section 和 References，基本可以把整个专业 PDF 入库链路都测一遍。论文最后的实验部分甚至还有功耗数据，例如最高 36.4 dB loss channel 下，digital equalizer 的 38 mW 中约 28 mW 可由 per-symbol dynamic enabling 节省。

如果这个级别的 PDF 能做到**图、文、公式、引用之间不丢关系**，再去处理普通技术文档就容易很多。
