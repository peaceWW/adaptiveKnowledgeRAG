# 芯片知识「图 → 公式 → 说明」落地方案

面向当前仓库实现，不推倒存储与抽取流水线。目标：芯片设计工程师检索架构类知识时，**先看到架构图，再看到相关公式，最后才是文字说明**，并能点回原 PDF。

---

## 1. 需求怎么理解

用户不是在要「多抽几张图」，而是要改变**知识消费顺序**：

| 工程师怎么想 | 系统现在怎么给 |
| --- | --- |
| 先看框图，建立结构 | 先生成一段文字，图挂在回答下面 |
| 再核对公式/抽头/约束 | 公式当普通文本命中，排序靠语义角色不是 kind |
| 最后读说明，对照出处 | 说明与图可能不在同一章节证据包里 |

典型问题：「混合接收机架构」应对 Fig.4（ADC with embedded 3-tap FFE）→ 相关 FFE 抽头公式 → 该图附近的原理/约束说明 → 原 PDF 页。

因此要改的是三件事，按优先级：

1. **展示顺序**：问答 / 图谱 / 目录的证据区按 `figure → equation → table → text`。
2. **检索捆绑**：命中一张图或一段说明时，把同章同页的图、公式、说明一起取回，而不是只取最相似的文字单元。
3. **意图分流**：架构/电路问题优先图；指标/对比问题可以先结论和曲线，再公式。第一期先覆盖架构类。

---

## 2. 对 `知识体系修改方案.md` 的可行性结论

**方向可行，不能当施工图整份落地。**

该文档把问题从「加图」提升到「工程知识单元 + 证据链」，这一点对芯片库是对的。但它建立在一个过时前提上：系统还是「Document → Chunk → 向量」。当前实现已经不是纯文本 Chunk RAG。

| 方案文档主张 | 当前仓库实际 | 落地建议 |
| --- | --- | --- |
| 核心对象从 Chunk 换成 Knowledge Unit | `KnowledgeUnit` + `unit_meta.kind`（figure/equation/table/concept）已是主对象 | **沿用，不要新建 EKU 表** |
| 图/公式/说明要有语义关系 | 已有 `BELONGS_TO` / `ILLUSTRATES` / `HAS_FIGURE` 等；图挂 `parent_anchor` | **用现有关系做章节级证据包，不先上 ILLUSTRATED_BY 新本体** |
| 图不能只 OCR，要语义描述 | 图单元已有 caption、Vision `Description`、`components`、`figure_type`、`image_url` | **补检索加权与展示，不重做解析** |
| 公式不能只存 LaTeX | 公式单元已有 latex / meaning / variables / nearby_text | **检索与展示按 kind 提前，不重抽** |
| MySQL + Vector + MinIO 三层 | 已是 Postgres/SQLite + Qdrant + 本地/MinIO | **不换存储** |
| 查询先理解再扩图/公式 | `QueryWorkflow` 已有 understand → plan → hybrid → expand_kinds | **改排序、完整性、邻居扩展配额** |
| 回答顺序：结论 → 图 → 公式 → 解释 | 与本次需求不一致 | **证据区按用户要求：图 → 公式 → 说明**；LLM 可在图前加一句工程结论 |
| 新表 knowledge_figure_relation 等 | 会与 `knowledge_relation` + `unit_meta` 重复 | **第一期禁止新表** |
| Chip Designer Retrieval Strategy 按问题类型换优先级 | `QueryIntent` 只有 definition/cause/solution/risk/comparison | **加 evidence_priority，不先加一堆新 Intent** |

一句话：方案文档是**目标架构白皮书**；本文件是**在现有 `QueryWorkflow` / `paper_extractor` / Chat·图谱·目录上可改的施工单**。白皮书里的 EKU、新关系本体、按问题类型换整套 UI，放到第三期。

## 3. 现状差距（对照代码）

抽取侧其实已经具备多模态单元：

- 图：`paper_extractor` 写出 `kind=figure`、截图 URL、组件与描述，并 `ILLUSTRATES` 到章节。
- 公式：`kind=equation`，带 LaTeX 与含义。
- 说明：章节语义单元 `kind=concept`，`parent_anchor` 指向同一节。

检索侧把这些资产用弱了：

- `_order_context_hits` 只按 `via`（parent / core / relation）排，**图不会因为是图而靠前**。
- 邻居扩展每种 kind 最多 3 条，且分数固定 0.4，容易被高分文字挤掉。
- 完整性检查只看 `semantic_role`，**不问有没有 figure**。
- `answer-generator.yaml` 要求「原理 → 约束 → 指标」，图只是「正文里提一句 image_url」。
- `ChatView` 先渲染 Markdown 回答，**图在回答下方「相关图片」**，和工程师扫图习惯相反。
- 图谱/目录证据卡按角色/过滤器排，没有 kind 优先。

所以「资料库里有 Fig.4，问架构却先出一段文字」是**排序和 UI 问题，不是没有抽图**。

---

## 4. 落地对象：章节证据包（不新增表）

不引入独立 EKU 实体。运行时把同文档、同 `parent_anchor`（或同 `source_chapter` + 页）的单元捆成一包：

```text
EvidenceBundle
  document_id
  parent_anchor / chapter / page
  figures[]     kind=figure，带 image_url
  equations[]   kind=equation，带 latex
  tables[]      kind=table
  texts[]       其余说明/原理/约束
  source        原 PDF document_id + page
```

问答、图谱、目录共用这一包的排序：`figures → equations → tables → texts`。

用户问「混合接收机架构」时的期望路径：

```text
向量/关键词命中 Fig.4 或「hybrid receiver」说明
        ↓
按 parent_anchor 扩同章 figure / equation / text
        ↓
UI：先 Fig.4 原图 → FFE 抽头公式 → 文字说明
        ↓
查看原 PDF 定位到该页
```

---

## 5. 明确不改什么

- 不换 Qdrant / 对象存储 / 知识单元主表。
- 不把图和公式合并进同一个 `content` 字段。
- 不重跑「整篇 PDF 塞进上下文」当默认检索。
- 第一期不新增 `knowledge_unit` 子表、不改上传向导、不改审核主流程。
- Markdown/TXT 没有图时：跳过图区，公式→说明；不要为此禁用检索。

## 6. 分期施工

### 第一期：筛选顺序 + 展示顺序（建议先做，可独立上线）

**后端 `backend/app/retrieval/workflow.py`**

1. 增加 `evidence_priority(query, intent)`：查询含「架构 / 框图 / 电路 / receiver / ADC …」或 intent=definition 时，kind 权重 `figure=3, equation=2, table=1.5, text=1`。
2. 改 `_order_context_hits`：同一包内按 kind 权重再按分数排；核心命中与 relation 邻居都走这套序。
3. `_expand_neighbors`：对每个核心命中，按 `parent_anchor` 或 `parent_id` 把同章 figure/equation 全部带上（可设上限 8，不要卡死在 3）。
4. 完整性：架构类问题若 hits 中无 `kind=figure`，记 missing=`figure`，触发二次检索（query 加 `Fig` / `architecture` / 章节名）。
5. `answer()` 传给模型的 context_blocks **先图后公式后文**，并标明 `【图】【公式】【说明】`。

**提示词 `backend/prompts/answer-generator.yaml`**

- 正文结构改为：一句工程结论 → **先描述图（Fig.N + 图中模块）** → 写出公式 Eq.(N) → 再写原理/约束。
- 禁止把图只放在文末「相关图」一行。
- 没有图时写「资料未覆盖架构图」，不要编图。

**前端问答 `frontend/src/views/ChatView.vue`**

- 回答区改为三块证据 + 一段 LLM 综述：
  1. **架构/电路图**（现有 `DocumentAsset`，提到最上面）
  2. **公式**（citation.kind=equation，渲染 latex/content）
  3. **说明**（其余 citation）
  4. 助手文字（可缩短，避免再复述一遍图）
- 「引用来源」保留；点标题打开现有「查看依据与原 PDF」弹窗。

**图谱 / 目录**

- 证据列表默认排序与问答相同；「全部」页里图卡置顶。
- 不改思维导图分类树（那是 taxonomy，不是证据结构）。

**验收**

- 问「混合接收机架构」：第一条可见证据是 Fig.4 类架构图，而不是纯文字卡片。
- 同屏能看到至少一条公式或明确「本节无公式」。
- 点图或「查看原 PDF」能落到对应页。

### 第二期：捆绑质量（抽取侧小改，仍无新表）

**`paper_extractor.py` / 图解读提示词**

- 图 `unit_meta` 补 `engineering_topic`（如 `hybrid_adc_receiver`），写入 embedding 文本（title+caption+components+topic）。
- 公式与邻近图：若同页或 caption 互指 Fig.N / Eq.N，写 `HAS_EQUATION` / `HAS_FIGURE`（关系表已支持）。
- 章节说明单元的 `concepts` 必须带上该节出现的 Fig/Eq 编号，便于关键词命中。

**向量载荷 `unit_vector_payload`**

- figure 的 `content` 前缀 `图:`，equation 前缀 `公式:`，避免和图注文字在向量空间里与普通段落无法区分。

**检索规划**

- `understand` JSON 增加 `evidence_types: ["figure","equation","text"]`。
- 架构问题 `required_roles` 不够时，用 required **kinds** 做完整度，而不是只查 definition/principle。

**验收**

- 只问「混合接收机」不提 Fig，仍能召回 Fig.4（靠 caption/components 向量 + 邻居扩展）。
- 问「三抽头 FFE 系数」先出公式截图/LaTeX，再出 Fig.9 电路，而不是先出摘要段。

### 第三期（可选）：白皮书中的 EKU 与策略矩阵

仅当第一、二期仍出现「图和说明对不上」时再做：

- 运行时把 EvidenceBundle 落成一种 `unit_meta.kind=eku` 的聚合单元（仍用同一张 `knowledge_unit` 表）。
- 按问题类型切换优先级：架构 `图>原理>公式`；电路 `电路图>状态>公式>参数`；指标 `结论>曲线>表>公式`；调试 `现象>波形>原因`。
- 不要为此拆 MySQL 新库。

## 8. 风险与边界

- **错配图**：只按全局相似度取「任意 ADC 图」会显得专业但不忠实。必须用 `parent_anchor` / 同页约束，禁止跨章凑图。
- **无图文档**：CDC markdown 等保持纯文字，完整度不要因为缺 figure 而判失败。
- **上下文变长**：同章扩展会增加 token。第一期上限：图 3 + 公式 4 + 说明 6。
- **旧数据**：已抽取文档一般已有 kind 与 image_url，第一期**不必全量重抽**；第二期语义字段才需要重抽论文。

---

## 9. 和需求的对应关系

需求：「以图片、公式、文字说明的顺序展示，并围绕这个顺序归纳。」

落地定义：

1. **归纳**：继续以现有 Knowledge Unit 为原子；用章节锚点把图/公式/说明收成一包（第二期补互指关系）。
2. **筛选**：检索后按 kind 重排 + 同章扩展，而不是只按向量分。
3. **展示**：问答、图谱、目录三条消费路径统一「图 → 公式 → 说明 → 原 PDF」。

这比新建一套 EKU 库更快验证工程师是否真的「先看见图」；验证成功后再决定要不要做第三期聚合单元。
